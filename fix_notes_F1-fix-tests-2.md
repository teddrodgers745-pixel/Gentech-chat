# fix_notes_F1-fix-tests-2

## Главное: чего не хватило для точного перечня падений
Приложенный «лог шага Run tests» содержит ТОЛЬКО сводку статусов шагов и
аннотации: «32 tests passed, 2 failed» + «Process completed with exit code 1».
Полный вывод flutter test (имена файлов/тестов/сообщения) в нём отсутствует.
Попытка забрать raw-лог из GitHub API/страницы job — HTTP 403/451 (логи
требуют авторизации, рендер-прокси недоступен). Поэтому «перечислить ВСЕ
падающие тесты» дословно невозможно — ниже приведены падения, выведенные
статически из кода, контракта F1 и истории фиксов. Всего тестов ровно 34
(совпадает с «32+2»), и все не-F1 тесты — прежние, зелёные на e1364fb;
падения почти наверняка в test/f1_retry_resume_test.dart + восстановление
ошибок по коду.

## Что сделано (2 файла)
1. lib/core/models/gen_error_mapper.dart — ИЗВЕСТНЫЙ НЕДОЧЁТ (обязательный
   пункт задачи): добавлен `case 'status_unknown': return
   JobStatusUnknown(details: details);` в GenErrorMapper.fromCode. Раньше
   карточка JobStatusUnknown после перезапуска восстанавливалась как
   UnknownGenError («Ошибка генерации» вместо «Статус задачи неизвестен»),
   и любой тест round-trip errorCode 'status_unknown' падал. Виноват КОД.
   jobId сознательно не передаётся (живёт в GenerationSnapshot).
2. test/f1_retry_resume_test.dart — F1-T-NETWORK-POLL-KEEPS-RECORD.
   Виноват ТЕСТ (фикстура), а не код. Фикстура отвечала 404 на все
   GET-опросы, а «сеть рвётся» моделировалась server.close(force: true)
   ПОСЛЕ await created.future — гонка: если первый опрос успевал
   достучаться до живого сервера, все 5 путей опроса получали 404, и
   исполнитель (корректно, по контракту «удаляется по фатальному») отдавал
   фатальный UnknownGenError «Задача не найдена (404/405)» и удалял запись —
   тогда как тест требует JobStatusUnknown и живую запись. Теперь опрос
   вообще не отвечает (соединение принято, ответа нет до force-close):
   исполнитель гарантированно получает сетевую ошибку опроса →
   транзиентный путь → JobStatusUnknown + живая запись, детерминированно.
   Код AsyncJobExecutor не менялся (404-как-фатальный — правильно).

## Остальные 2 теста F1 (RESUME-SAME-JOB, POLLER-TRANSIENT-RETRIES, CARD-TEXT)
Проверены статически построчно против контракта F1 и кода исполнителей —
нарушений не найдено (RESUME: resumeJob → только GET, polling → completed →
материализация → remove; POLLER: 3 вызова/['done-1'] и hardCalls=2;

## Что стоит улучшить рядом (не чиня сейчас)
- GenerationService.resumeJob/restorePendingJobs: `catch (_) {}` глотает
  ошибки потока — лучше логировать (или пробрасывать наружу после снятия
  PendingPart), иначе молчаливые падения материализации невидимы.
- Для не-Polza провайдеров 404 сразу после создания задачи трактуется как
  фатальная — на фоне eventual consistency провайдера можно дать одну
  «грацию» (отложить фатальность 404 на первые N секунд жизни задачи).
- poller: `onTransientRetry` колбэк у AsyncJobExecutor._watch пишет JSONL
  вне сериализации очереди ActiveJobsStore — не критично.

## Как проверить живым тестом
1. F1-LIVE-RETRY-RESUME (регрессия): запустить генерацию видео, в середине
   опроса включить авиарежим на 20–30 с, включить сеть → карточка должна
   показать «Статус задачи неизвестен» (НЕ «Ошибка генерации» и НЕ
   «Ошибка соединения»), «Повторить» продолжает опрос той же задачи:
   в списке провайдера — одна задача, без второго списания.
2. Перезапуск приложения с незавершённой задачей → после перезапуска
   карточка ОСТАЁТСЯ «Статус задачи неизвестен» (проверка fromCode-фикса),
   «Повторить» → видео доезжает до чата.
3. F1-LIVE-IMAGE-RELOAD (регрессия): готовая картинка с недоступным
   временно URL → карточка показывает «Не удалось загрузить изображение»
   с авто-повтором загрузки, без запуска новой генерации.
