# fix_notes_F1-retry-resume.md — замечания по задаче F1-retry-resume

## Что было не так (по трассировке UI → сервис → исполнитель → API)

Кнопка «Повторить» в карточке ошибки генерации идёт в `_regenerate()`
(chat_screen.dart), который снимает ошибочный ответ, читает
`GenerationSnapshot` из user-сообщения и вызывает `_generateVideo` /
`generateImage`. Эти методы уже умеют resume по `snapshot.jobId`
(`GenerationService.resumeJob` → `AsyncJobExecutor.resume` → только
GET /media/{id}), но путь был дырявым в трёх местах:

1. **`snapshot.jobId` заполнялся из ЛЮБОГО `GenerationFailure`** — включая
   фатальные (failed/404/таймаут лимита/отмена). Повтор тогда возобновлял
   МЁРТВУЮ задачу: опрос падал 404/failed снова и снова, вместо честного
   создания новой. Обратная сторона требуемой логики «повтор живой задачи
   = продолжить»: фатальная ошибка обязана СБРАСЫВАТЬ jobId в снимке.
2. **Если `snapshot.jobId` оказывался пуст** (приложение убито до первого
   `GenProgress` с jobId, или снимок сохранён раньше, чем пришёл jobId) —
   повтор молча делал НОВЫЙ POST /v1/media → новая задача → новая
   резервация. Это и есть наблюдённое «дважды нажал — две новые задачи».
3. **Картинка с временно недоступным URL** (completed, но DNS картинки
   лежал): плейсхолдер «Не удалось загрузить изображение» не имел
   повторной загрузки — любой повтор означал новую генерацию и новое
   списание, хотя сама картинка была уже готова у провайдера.

## Что поправил

- **chat_screen.dart** (`_generateVideo`, `_generateImage`):
  `GenerationFailure` теперь различается по типу. `JobStatusUnknown`
  (транзиентная сетевая ошибка ОПРОСА) — jobId СОХРАНЯЕТСЯ в снимке,
  «Повторить» продолжает опрос ТОЙ ЖЕ задачи. Фатальная ошибка —
  jobId из снимка сбрасывается, повтор создаёт новую задачу.
- **chat_screen.dart** (`_regenerate`): если jobId в снимке пуст, живая
  задача ищется в `ActiveJobsStore` по модели+промпту
  (`GenerationService.findLiveJobId`) — вместо молчаливого нового POST.
  Записи проваленных задач из хранилища удаляются при фатальной ошибке,
  поэтому «живой» может быть только реально живая задача.
- **async_job_executor.dart / images_api_executor.dart**: jobId события
  ошибки прикрепляется ТОЛЬКО к `JobStatusUnknown` — фатальные больше
  не несут jobId для «повтора мёртвой задачи». TEMP-DIAG-UNMODIFIABLE
  не тронут.
- **gen_error.dart**: `JobStatusUnknown.message` теперь явно говорит:
  задача создана и продолжает выполняться у провайдера, «Повторить»
  продолжит ожидание той же задачи без нового списания (а не «проблемы
  с сетью» вообще).
- **message_view.dart**: сетевые картинки (`_PartImage` и `_MarkdownImage`)
  рендерятся через новый `_RetryableNetworkImage`: при ошибке загрузки —
  автоповтор ЗАГРУЗКИ того же URL с нарастающей паузой
  (2/4/8/15/30/60/120 c, evict из imageCache, уникальный ключ попытки)
  и кнопка «Повторить загрузку». Новая генерация НЕ запускается —
  это соответствует живому наблюдению «через 3–4 минуты картинка
  появилась сама».
- **generation_service.dart**: добавлен `findLiveJobId({model, prompt})` —
  поиск живой записи в ActiveJobsStore для повтора без нового списания.
- **Проверено по коду** (п.4 приёмки): запись задачи НЕ удаляется из
  ActiveJobsStore при `PollTransientFailure` (удаление — только
  fatal/done/cancel/timeout); `restorePendingJobs()` подхватывает её при
  перезапуске приложения. Закрыто тестом `F1-T-NETWORK-POLL-KEEPS-RECORD`.

## Тесты (test/f1_retry_resume_test.dart)

- `F1-T-RESUME-SAME-JOB`: resumeJob по сохранённому jobId — НОЛЬ POST
  /media, опрос ТОГО ЖЕ jobId, завершение тем же jobId, запись убрана
  из хранилища после done.
- `F1-T-NETWORK-POLL-KEEPS-RECORD`: обрыв сети во время опроса (реальный
  HttpServer, закрытый после create) → ровно ОДИН POST, ошибка —
  `JobStatusUnknown` с jobId, запись жива в ActiveJobsStore; повтор по
  jobId — снова ноль POST. (~13 c из-за пауз 2/4/6 c в бэкоффе.)
- `F1-T-POLLER-TRANSIENT-RETRIES`: семантика `MediaStatusPoller` —
  транзиентные сбои переживаются внутри попытки, исчерпание повторов
  кидает `PollTransientFailure` наружу.
- `F1-T-CARD-TEXT`: текст карточки различает «сеть оборвалась, задача
  жива» и «повтор без нового списания».

## Чего не хватило в присланном коде

Не присланы: `generation_event.dart` (конструкторы событий —
использовал только те, что видел в коде), `artifact_materializer.dart`
(поведение materializeVideo при сбоях), `storage.dart`/`app_state.dart`
(когда именно `store.save()` сериализует снимок). Если фактические
конструкторы/тайминги отличаются — возможна правка теста по логу CI.

## Живая проверка (после зелёной сборки)

- **F1-LIVE-RETRY-RESUME**: Seedance 480p, во время опроса включить
  airplane-mode/выключить Wi-Fi → карточка «Статус задачи неизвестен»
  («задача продолжает выполняться… без нового списания»), сеть вернуть,
  нажать «Повторить» ДВАЖДЫ — в чате растёт прогресс ТОЙ ЖЕ задачи,
  в кабинете Polza ровно ОДНА резервация (счётчик запросов не растёт).
  Перезапустить приложение с «оборванной» задачей — карточка
  восстанавливается и опрос продолжается сам (restorePendingJobs).
- **F1-LIVE-IMAGE-RELOAD**: Flux, дождаться completed, но URL картинки
  временно недоступен (или выключить сеть до появления картинки) —
  плейсхолдер с кнопкой «Повторить загрузку»; вернуть сеть — картинка
  появляется сама (автоповтор), в кабинете Polza НЕ появляется новых
  генераций.

## Что стоит улучшить рядом (не чиню сейчас)

- При потере ответа на POST-create (create «повис», но задача на сервере
  создана) jobId узнать невозможно — повтор сделает новую задачу с
  новой резервацией, а «осиротевшая» останется в кабинете. Лечится
  серверным idempotency-key в теле создания; TEMP-DIAG не трогал.
- `ImagesApiExecutor` не пишет записи в ActiveJobsStore — image-задачи
  не переживают перезапуск приложения, возобновляются только «повтором»
  по jobId из снимка. Сохранение image-записей дало бы полный паритет
  с видео.
- `_onRestoredEvent` при транзиентной ошибке восстановленной задачи
  снимает PendingPart и превращает сообщение в карточку ошибки; можно
  оставить «в процессе…» с кнопкой «Продолжить ожидание» — UX-задача.
- `findLiveJobId` матчит по модели+промпту: два ОДНОВРЕМЕННЫХ живых
  видео-запроса с одинаковым промптом и моделью при повторе без jobId
  сольются в одну задачу. Практика редкая, но стоит знать.
